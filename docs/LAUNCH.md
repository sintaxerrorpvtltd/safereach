# Poki — by Sintax Error · launch notes

Draft creative materials only. No social post, account, app, ad or third-party
message is authorized or sent by this document. The name is provisional.

Position Poki as a playful, opt-in way to say a little hello across participating
surfaces. This release is a public static site with a fictional same-tab demo.
Remote delivery, embed SDK, external channels and Pro remain planned. Use no
private source conversations, personal circumstances or founder help-seeking story.
Earlier trusted-handoff experiments stay in separate technical documentation.
Instagram DMs and Telegram are planned priorities; WhatsApp is outside this MVP.
Codex has an experimental MCP reference; Claude Code and OpenCode remain candidates.
The onboarding direction is “Sign in → choose connection → guided setup → test”,
but no sign-in or working channel-connect flow exists in this static release.

## Three reel concepts

1. **Different tabs. Still connected.** Open with two fictional corners, Alex and
   Sam, then show the actual pairing → preview → approval → Poki wave flow. Keep
   “Fictional same-tab demo · remote delivery planned” visible throughout. The hook
   describes the product direction; never edit the local demo into fake live remote
   delivery or claim an existing Codex chat was interrupted.
2. **A hello, not a whole speech.** Poki peeks in, the literal “Hi!” is previewed,
   and the user approves. End with Do Not Disturb being switched on: connection
   stays a choice. No emotional pressure, emergency language or implied reply duty.
3. **Make Poki a little more you.** Show the locally drawn mascot beside its SVG
   source, then a fictional contributor’s UI/character idea becoming a pull request.
   Label any unmerged concept. End on “Open-source core. Community contributions
   welcome. By Sintax Error.” Do not imply automatic merge or a released SDK.

## Staged launch checklist

1. Verify public Pages URL, exact commit, mobile/desktop, controls and reduced motion.
2. Check README/PRD/license, status labels, privacy boundary and contribution path.
3. Capture only actual implemented behavior with the persistent local-demo label.
4. Review captions and links; get separate approval for any social publication.
5. Invite repository feedback; review/test PRs before merge. Do not promise Pro
   availability, a delivery SLA or specific third-party adapter launch dates.
6. Consider remote transport reuse only in a separately authorized and reviewed
   milestone. Publish a new verified status before marketing any new capability.
